# Design Document: hr-desk

- `agents/tiers/read-only.json`, `agents/tiers/write-in-worktree.json`: the only source of `tools` and `permissions.rules` (today's role agent files are split into tier + persona).
- `src/team/generate.ts`: `agentFileFor(member, template, tier)` → `{ name, description, prompt: persona + role instructions, model, tools: tier.tools, permissions: tier.permissions }`; written to `data/kiro-home/agents/<projectId>-<memberId>.json`; `kiro-cli agent validate --path` on write.
- `src/team/store.ts`: `data/teams.json` `{ [projectId]: Member[] }`, `Member { id, displayName, templateId, role, model }`; default team created on registration.
- `src/team/import.ts`: fetch only allowlisted URLs (HTTPS, 64 KB cap, 10 s timeout), parse with a strict zod schema after copying only known safe fields, `leaks.scanText`, then queue for review; `import-review.ts` runs `agentlife-import-review` (not `agentlife-security`, see "Review" under task 3 and D10) with a fixed prompt and stores its verdict; approval stores `sha256(content)`.
- Pipeline integration: the JobRunner resolves each role step to the team member with that role (first one), so a project can run with a renamed or differently modelled agent; `reviewer` and `researcher` roles are used by pipeline-editor.
- Client: `ui/hr.ts` (tabs: Catalogue, Teams, Imports), HR ghost tooltip; floors show members by display name.

## Decisions made while implementing (tasks 1–2)

- Where things live: tiers in `packages/agent-engine/agents/tiers/`, catalogue in `packages/agent-engine/config/catalogue/` (one file per template, the file name is the template id), allowed models per role in `config/team-rules.json`. Shared schemas (template, member, API bodies) are in `packages/shared/src/team.ts`.
- Prompt = `persona + " " + ROLE_INSTRUCTIONS[role]`. The role instructions (read-only wording, untrusted-data rule, output format) are fixed text in `team/generate.ts` and come after the persona. The three committed `agentlife-*.json` role agents are exactly what the generator produces for the built-in templates; a test fails if they drift.
- `agentFileFor(spec, template, tier)` parses the template with the non-strict base schema (only known fields are read), takes `tools` and `permissions` from the tier alone, and refuses a tier that is not the role's (`developer` → `write-in-worktree`, every other role → `read-only`). Catalogue files are parsed strictly and must carry the role's tier.
- Agent files are checked in `<kiroHome>/agents-staging/` with `kiro-cli agent validate` and moved into `agents/` only when the check passes. An identical file is left alone and not checked again. Names are `^[a-z0-9][a-z0-9-]*$` (they become file names and `--agent` values).
- Default team: a project with no entry in `data/teams.json` has Architect, Developer and QA running the built-in `agentlife-<role>` agents with the models of `config/agents.json`. The first change (hire, rename, model, fire) stores the whole team, and from then on every member runs on a generated file `<projectId>-<memberId>.json`. A project whose id would give a name starting with `agentlife-` cannot be customised (it would overwrite a built-in agent).
- Roles `reviewer` and `researcher` can be hired and stored but no step uses them yet (pipeline-editor). Their activity lines come from the QA and Architect seat of the floor, because only three seats exist in a room.
- A step asks `TeamService.resolve(projectId, taskId, role)`. The first call of a job reads the whole team and keeps it for that job (up to 200 jobs), so renaming, a new model or a firing applies from the next job. A role with no member (QA fired) gives `undefined` and the step runs the built-in agent.
- Firing is refused for the only architect or developer (`last_of_role`) and for the member a running job uses in the role that is working now (`agent_working`: states analyzing → architect, developing → developer, reviewing → QA). Agent files are not deleted when someone is fired (a running job may still need the file); `syncAgents` at engine start writes missing files without validating and removes the files of members that no longer exist.
- Models: a hire or change must be in the role's list of `team-rules.json` and in the account's list (`kiro-cli chat --list-models --format json`, cached 5 minutes, read with the same minimal environment as the role agents). If kiro-cli cannot list models the change is refused (`models_unavailable`). Under `RUNTIME=fake` the only model is `fake`. Model ids and agent names are checked again in `KiroCliRuntime.buildArgs` so nothing that looks like a flag reaches the command line.
- Changes of one engine are serialised (hire/update/fire never overlap). Routes: `GET /catalogue`, `GET /team/models`, `GET|POST /projects/:id/team`, `PATCH|DELETE /projects/:id/team/:memberId`. Removing a project drops its team.
- Activity lines use task id `team:<projectId>` and the agent id `<projectId>:<role>`, like the Builder uses `build:<session>`.

## Decisions made while implementing (task 3)

- **Sources.** `config/catalogue-sources.json` is `{ "sources": [https address, ...] }`, empty by default. Each entry is the address of one template file and is matched exactly after normalising (`new URL(...).href` without the fragment). Plain http, other schemes and addresses with credentials are never allowed. The fetch (`import.ts`) sends no credentials, does not follow redirects (a redirect could leave the list), waits 10 s and stops reading at 64 KB, also when the body does not declare a size. The engine never shows the address in a fetch error.
- **What is kept.** Only `id`, `name`, `role`, `persona`, `description` and `defaultModel` are copied (by name, with `Object.hasOwn`, so a `__proto__` or `constructor` key does nothing). `tier` is computed from the role and `source` is the address; a file that carries another `tier` has `tier` listed as ignored. Every other field name is returned in `ignored` (at most 30, names with odd characters are shown as "(field with an unusual name)"). Over-long persona or description is refused, not cut: cutting would change what the author wrote. Text with control, zero-width or direction-changing characters is refused. Text where the leak scanner finds a high or medium finding (keys, tokens, e-mail addresses) is refused, naming the kind and never the value.
- **Review.** The design said to run `agentlife-security`. That agent is the developer's own (it can write under `data/security` and run git commands), so it is not given text from the internet. The hotel has its own `agentlife-import-review`, made by `service-agents.ts` from a template and the read-only tier (like any team member, so its permissions are the tier's by construction), run in an empty directory with the template in fences (`prompts/import-review.md`). The prompt covers what the security agent would look for. The review is advice: the verdict `pass` or `concerns` and the flags are shown to the user, and nothing is approved by it. The fixed checks (`checkTemplateText`, a list of patterns for "ignore previous instructions", tool or permission requests, secrets, web addresses, sending data out, skipping approval) always run and cost nothing; the agent runs on top when the pipeline is real. If the agent fails or is not running, the review says only the automatic checks ran.
- **Approval.** `data/catalogue-imports.json` keeps, per template id, the version fetched last (`current`) and the version the user approved (`approved`, with its hash and time). `approve` carries the hash the user was shown and fails with 409 `content_changed` if the current hash is different. Only the approved version is in the catalogue. A new fetch with different content gives `update_pending`: the approved version stays hireable (teams that already use it keep working, and `commit` can still write their agent files), the new one waits for a new approval. `reject` drops the waiting version; a template never approved is removed. When the file is read, each approval is checked against its stored hash and loses the approval if the content was edited on disk.
- **Ids.** An imported id cannot be a built-in id, and cannot be the id of a template imported from another address.
- **Routes.** `GET /catalogue/sources`, `GET /catalogue/imports`, `POST /catalogue/imports { url }`, `POST /catalogue/imports/:id/approve { hash }`, `POST /catalogue/imports/:id/reject`. The import call waits for the review (up to 90 s with the agent).
- **Not run live:** the real security review with kiro-cli, and a real download. Tests use a stubbed fetch and a scripted runtime.

## Decisions made while implementing (task 4)

- **Protocol.** Client `hr_state` (read the desk) and `hr_do { act }`, where `act` is `HrActionSchema` (`hire`, `update`, `fire`, `import`, `approve_import`, `reject_import`, `suggest`, `apply`). Server `hr { state }` (catalogue, a team per project, imports, sources, models), `hr_suggestion`, `team_view { roomId, members }` and `agent_presence { agentId, present }`; error code `hr_error`. Panel and interaction `hr`, furniture `hr_desk` (2x1, north wall of the HR office). All the shapes are in `shared/src/hr.ts`. `hr_do` is accepted only while the user is in the HR office; `hr_state` anywhere.
- **Engine link.** `EngineLink.hr` is one optional object (`HrLink`): the scripted engine and the demo have none, and the panel then says the HR desk needs the real engine (or is off in the demo). `HttpEngineLink.hr.state()` joins `/catalogue`, `/projects`, each team, `/catalogue/imports`, `/catalogue/sources` and `/team/models`. Import and suggestion calls wait up to 120 s (the security agent and the HR agent run behind them).
- **HR agent.** `POST /projects/:id/team/suggest` (`team/suggest.ts`). The HR agent (`agentlife-hr`, made from the read-only tier like the import reviewer, run in an empty directory, `prompts/hr-suggest.md`) only names templates and gives a reason each. The engine decides what is a valid pick: a catalogue template for a role that has a desk (architect, developer, qa), not the template that holds the desk already, one pick per role, at most three, a model the role may use, a name nobody on the team has. When the agent is not running or fails, fixed rules choose from the project's stack and size (`git ls-files` count: under 60 files a Fast QA, 300 or more a Thorough Architect and a Strict QA, no runnable tests a Strict QA) and the proposal says `by: "rules"`. Nothing is hired by asking.
- **Apply.** The user presses "Apply this team": the gateway hires each pick and then fires the member it replaces (in that order, so the team never lacks a role), and stops at the first refusal. The proposal is applied by the user's own `apply` action; the picks are validated again by the engine's hire and fire rules.
- **Who sits at a desk.** A project floor has three desks. The first member of a role works that role's desk (this is also the member the jobs use); other members of the role are "on the bench" in the HR panel, and reviewers and researchers have no desk yet (pipeline-editor gives them one). So a hire becomes visible on the floor when it takes a desk: the ghost carries the member's name and model (`team_view`, also in its tooltip). When a different person takes a desk (the holder was fired, or a proposal replaced them), the old ghost walks to the elevator and disappears (`agent_presence false` after a `walk` to the door), and the new one comes back through the elevator and walks to the desk (`agent_presence true`, new name, walk home) about 0.7 s after the old one arrived. The gateway keeps who the engine says sits where (`seatsNow`) and what the room shows (`seatsShown`); a ghost that is out when the user arrives on the floor is kept out until it returns. The sequence runs in the simulation whether or not the user is on that floor. A rename changes the name tag with no walk. The team bar keeps the role names.
- **HR ghost.** Scenery in the client only (`WorldView.addHrGhost`, pink, next to the HR desk): the simulation has no HR agent, so `roomAgents` of the HR office is still empty and the team bar stays empty there. It thinks while a proposal is being worked out.
- **Not done / limits.** A hire of a second member of a seated role does not show on the floor (it waits on the bench). The walk out and back is not looked at in a browser with a real engine; the browser check covered the HR office rendering (screenshot) and the elevator. The security review and the HR agent have not been run with a real `kiro-cli`.
- **Test isolation.** `packages/agent-engine/vitest.config.ts` now gives each run its own folder for the default projects, teams and imports files (`AGENTLIFE_*_FILE`), because a test that hired a member through the default teams file left it for the next run.

## Decisions made while implementing (task 5)

- **The template says how it runs.** `Template.runtime` is optional: `kiro-cli` (absent) or `ollama`. `TemplateSchema` accepts `ollama` only for a built-in researcher, so no other role and no imported template can have it. An import never copies the field (`parseImport` picks known fields by name), and a file that carries `runtime` has it listed as "ignored for safety". `night-intern` (`config/catalogue/night-intern.json`) is the only template that uses it: role `researcher`, tier `read-only`, model `qwen3.5:4b`. The catalogue listing and the HR Catalogue tab show `runtime` ("runs on this computer, free").
- **`LlmRuntime` is not used.** The existing `LlmRuntime` is the ambient chatter (one line, 60 tokens, screened for links). The intern needs full answers, so `runtimes/ollama.ts` has its own `OllamaRuntime`: `POST <OLLAMA_URL>/api/chat`, no streaming, no thinking, the member's persona as the system message, the answer and the token count back. No tools exist on this path at all. Only an address on this computer (`localhost`, `127.x.x.x`, `::1`, no credentials) is ever used, because the prompt holds project text: any other `OLLAMA_URL` counts as "not available" and the fallback runs. It reads `OLLAMA_URL` like `scripts/notify.ts` (default `http://127.0.0.1:11434`).
- **Model ids may hold a colon** (`MODEL_ID_RE`), for Ollama tags. Still no leading dash, no spaces, no slash. A model of a kiro-cli member is still checked against the role's list and the account's list; the intern's model is not (it is not an account model) and may be changed to another local tag.
- **Only some steps.** `team/intern.ts` has `INTERN_STEPS = summary, overview, memory, classify`. `InternRuntime.run` refuses any other step name, and a call with no step name, with `InternNotAllowedError` before the local model or the fallback are touched; `runRole` checks the same when the member it resolved is the intern (a plan, develop or review step can never reach it). `RuntimeInput` has `step` (set by `runRole`) and `system` (the persona) for this. Nothing in the pipeline asks for a researcher yet: `analyze`, `develop` and `review` ask for architect, developer and QA, so today only the guard and the tests exercise the path. pipeline-editor and project-memory will call it with the four step names.
- **Fallback.** When the local model cannot answer (Ollama not running, model not installed, 120 s without an answer, an empty answer, a non-local address) `InternRuntime` yields `{ kind: "fallback", from, to, reason }` and runs the same prompt through kiro-cli with the member's own agent file and `claude-haiku-5.5`. The agent file of an intern is generated like any other (read-only tier, persona plus role instructions) and names `claude-haiku-5.5` as its model, since an Ollama tag would not validate; it exists only for the fallback. A cancellation, or an error that is not about the local model, is not answered with a fallback.
- **The report says so.** `runRole` writes the `fallback` event into the step's run log, sends a terminal line ("claude-haiku-5.5 does the overview step: ...") and adds a note to `JobNotes` (`steps/notes.ts`, in memory, 200 jobs). `reportStep` passes the notes to `buildReport`, which prints a `## Notes` section before `## Run facts` in every kind of report ("<name> runs on qwen3.5:4b. The local model is not running. The overview step ran on claude-haiku-5.5 instead, which spends credits."). The notes are lost if the engine restarts; the job in flight is failed at restart anyway.
- **Wiring.** Only the real pipeline builds an `InternRuntime` (local `OllamaRuntime`, fallback the service `KiroCliRuntime`) and passes it with the notes in `PipelineDeps`. Under `RUNTIME=fake` a team with the intern cannot run an intern step ("not available in this engine").
- **Not done.** The morning overview of the night shift still goes through `scripts/notify.ts`, which talks to Ollama itself and skips the overview when Ollama is down; it does not use this runtime. Moving it onto the intern (and so onto the fallback and the report note) needs the summary text to come through the engine, and belongs with project-memory or a night-shift follow-up. No live run: Ollama and `qwen3.5:4b` were not started, and the fallback was not run with a real `kiro-cli`.
