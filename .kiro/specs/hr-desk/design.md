# Design Document: hr-desk

- `agents/tiers/read-only.json`, `agents/tiers/write-in-worktree.json`: the only source of `tools` and `permissions.rules` (today's role agent files are split into tier + persona).
- `src/team/generate.ts`: `agentFileFor(member, template, tier)` → `{ name, description, prompt: persona + role instructions, model, tools: tier.tools, permissions: tier.permissions }`; written to `data/kiro-home/agents/<projectId>-<memberId>.json`; `kiro-cli agent validate --path` on write.
- `src/team/store.ts`: `data/teams.json` `{ [projectId]: Member[] }`, `Member { id, displayName, templateId, role, model }`; default team created on registration.
- `src/team/import.ts`: fetch only allowlisted URLs (HTTPS, 64 KB cap, 10 s timeout), parse with a strict zod schema after copying only known safe fields, `leaks.scanText`, then queue for review; `review.ts` runs `agentlife-security` with a fixed prompt and stores its verdict; approval stores `sha256(content)`.
- Pipeline integration: the JobRunner resolves each role step to the team member with that role (first one), so a project can run with a renamed or differently modelled agent; `reviewer` and `researcher` roles are used by pipeline-editor.
- Client: `ui/hr.ts` (tabs: Catalogue, Teams, Imports), HR ghost tooltip; floors show members by display name.

## Decisions made while implementing (tasks 1–2)

- Where things live: tiers in `packages/agent-engine/agents/tiers/`, catalogue in `packages/agent-engine/config/catalogue/` (one file per template, the file name is the template id), allowed models per role in `config/team-rules.json`. Shared schemas (template, member, API bodies) are in `packages/shared/src/team.ts`.
- Prompt = `persona + " " + ROLE_INSTRUCTIONS[role]`. The role instructions (read-only wording, untrusted-data rule, output format) are fixed text in `team/generate.ts` and come after the persona. The three committed `agentlife-*.json` role agents are exactly what the generator produces for the built-in templates; a test fails if they drift.
- `agentFileFor(spec, template, tier)` parses the template with the non-strict base schema (only known fields are read), takes `tools` and `permissions` from the tier alone, and refuses a tier that is not the role's (`developer` → `write-in-worktree`, every other role → `read-only`). Catalogue files are parsed strictly and must carry the role's tier.
- Agent files are checked in `<kiroHome>/agents-staging/` with `kiro-cli agent validate` and moved into `agents/` only when the check passes. An identical file is left alone and not checked again. Names are `^[a-z0-9][a-z0-9-]*$` (they become file names and `--agent` values).
- Default team: a project with no entry in `data/teams.json` has Architect, Developer and QA running the built-in `agentlife-<role>` agents with the models of `config/agents.json`. The first change (hire, rename, model, fire) stores the whole team, and from then on every member runs on a generated file `<projectId>-<memberId>.json`. A project whose id would give a name starting with `agentlife-` cannot be customised (it would overwrite a built-in agent).
- Roles `reviewer` and `researcher` can be hired and stored but no step uses them yet (pipeline-editor). Their activity lines come from the QA and Architect seat of the floor, because only three seats exist in a room.
- A step asks `TeamService.resolve(projectId, taskId, role)`. The first call of a job reads the whole team and keeps it for that job (up to 200 jobs), so renaming, a new model or a firing applies from the next job. A role with no member (QA fired) gives `undefined` and the step runs the built-in agent.
- Firing is refused for the only architect or developer (`last_of_role`) and for the member a running job uses in the role that is working now (`agent_working`: states analyzing → architect, developing → developer, reviewing → QA). Agent files are not deleted when someone is fired (a running job may still need the file); `syncAgents` at engine start writes missing files without validating and removes the files of members that no longer exist.
- Models: a hire or change must be in the role's list of `team-rules.json` and in the account's list (`kiro-cli chat --list-models --format json`, cached 5 minutes, read with the same minimal environment as the role agents). If kiro-cli cannot list models the change is refused (`models_unavailable`). Under `RUNTIME=fake` the only model is `fake`. Model ids and agent names are checked again in `KiroCliRuntime.buildArgs` so nothing that looks like a flag reaches the command line.
- Changes of one engine are serialised (hire/update/fire never overlap). Routes: `GET /catalogue`, `GET /team/models`, `GET|POST /projects/:id/team`, `PATCH|DELETE /projects/:id/team/:memberId`. Removing a project drops its team.
- Activity lines use task id `team:<projectId>` and the agent id `<projectId>:<role>`, like the Builder uses `build:<session>`.

## Decisions made while implementing (task 3)

- **Sources.** `config/catalogue-sources.json` is `{ "sources": [https address, ...] }`, empty by default. Each entry is the address of one template file and is matched exactly after normalising (`new URL(...).href` without the fragment). Plain http, other schemes and addresses with credentials are never allowed. The fetch (`import.ts`) sends no credentials, does not follow redirects (a redirect could leave the list), waits 10 s and stops reading at 64 KB, also when the body does not declare a size. The engine never shows the address in a fetch error.
- **What is kept.** Only `id`, `name`, `role`, `persona`, `description` and `defaultModel` are copied (by name, with `Object.hasOwn`, so a `__proto__` or `constructor` key does nothing). `tier` is computed from the role and `source` is the address; a file that carries another `tier` has `tier` listed as ignored. Every other field name is returned in `ignored` (at most 30, names with odd characters are shown as "(field with an unusual name)"). Over-long persona or description is refused, not cut: cutting would change what the author wrote. Text with control, zero-width or direction-changing characters is refused. Text where the leak scanner finds a high or medium finding (keys, tokens, e-mail addresses) is refused, naming the kind and never the value.
- **Review.** The design said to run `agentlife-security`. That agent is the developer's own (it can write under `data/security` and run git commands), so it is not given text from the internet. The hotel has its own `agentlife-import-review`, made by `service-agents.ts` from a template and the read-only tier (like any team member, so its permissions are the tier's by construction), run in an empty directory with the template in fences (`prompts/import-review.md`). The prompt covers what the security agent would look for. The review is advice: the verdict `pass` or `concerns` and the flags are shown to the user, and nothing is approved by it. The fixed checks (`checkTemplateText`, a list of patterns for "ignore previous instructions", tool or permission requests, secrets, web addresses, sending data out, skipping approval) always run and cost nothing; the agent runs on top when the pipeline is real. If the agent fails or is not running, the review says only the automatic checks ran.
- **Approval.** `data/catalogue-imports.json` keeps, per template id, the version fetched last (`current`) and the version the user approved (`approved`, with its hash and time). `approve` carries the hash the user was shown and fails with 409 `content_changed` if the current hash is different. Only the approved version is in the catalogue. A new fetch with different content gives `update_pending`: the approved version stays hireable (teams that already use it keep working, and `commit` can still write their agent files), the new one waits for a new approval. `reject` drops the waiting version; a template never approved is removed. When the file is read, each approval is checked against its stored hash and loses the approval if the content was edited on disk.
- **Ids.** An imported id cannot be a built-in id, and cannot be the id of a template imported from another address.
- **Routes.** `GET /catalogue/sources`, `GET /catalogue/imports`, `POST /catalogue/imports { url }`, `POST /catalogue/imports/:id/approve { hash }`, `POST /catalogue/imports/:id/reject`. The import call waits for the review (up to 90 s with the agent).
- **Not run live:** the real security review with kiro-cli, and a real download. Tests use a stubbed fetch and a scripted runtime.
