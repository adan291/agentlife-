# Design Document: pipeline-editor

- `shared/src/pipeline.ts`: `PipelineSchema`, `validatePipeline(p, team) → { ok } | { ok: false, errors: { index, rule }[] }` (pure, used by both engine and client for live feedback).
- `agent-engine/src/jobs/pipeline-runner.ts`: builds the transition table from a validated pipeline (each step kind maps to an existing step function); the JobRunner takes the table instead of the fixed one. The fixed table stays as the default and as a test oracle.
- Research step: `steps/research.ts` (read-only member, output `research.md` artifact, injected into the plan prompt as data).
- Second review: `steps/review.ts` reused with another member; `Review` artifacts per reviewer; report section "Reviews".
- Client: `ui/pipeline-editor.ts` inside the board panel; drag and drop with pointer events plus Up/Down buttons for keyboard use.

## Decisions made while implementing (tasks 1–2)

### The rules and what they leave free
- Each kind appears at most once. Plan, Approval, Develop, Tests, Review and Report are required; Research and Second review are optional. Requirement 1.2 does not say that Tests and a Review must exist; they are required here because the report's verdict rests on them and a job that builds without checking anything is not what the product promises.
- The rules fix almost the whole order: `[research] plan approve develop test review|second-review report`. The only free choices are which optional steps are in, who does each step, and whether the second review runs before or after the review. The board editor (task 3) still lets the user drag and press Up/Down, and shows the rule that blocks a bad position; most positions are blocked by design, because they are the safety rules.
- Roles per step (`PIPELINE_STEP_ROLES`): research `researcher`; plan `architect`; develop `developer`; review `qa` or `reviewer`; second review `reviewer` or `qa`. Approval, Tests and Report take no member (the user, the engine and a template do them). A step without `memberId` uses the first member of its role, as today; Research and Second review need a researcher / reviewer on the team, so the pipeline is refused until one is hired (the message points to the HR desk).
- The second review must be done by another member than the Review and on another model (requirement 3.2). The check compares the models of the two members (`team.json`), so with the default team (QA and the hired Reviewer both on `claude-haiku-5.5`) the user changes one model first. The error says so.
- The Night intern (local model, a `researcher`) is accepted by the rules as a researcher but cannot do the research step: `assertInternStep` refuses any step other than its four small ones, because it has no tools. The job fails at that step with the intern's own message. Not blocked in the validator, which does not know templates; a later change can pass a `local` flag.

### State machine (requirement 1.3)
- No new `JobState`. Research runs inside `analyzing` (before the plan) and the second review inside `reviewing`, so the world-server, the stepper, the board and the demo keep working on the same states for every pipeline. `stateFlowOf(pipeline)` maps each step to its state and merges neighbours that share one; `transitionsOfPipeline` feeds that flow to `buildTransitions` (the function the job kinds already use). For every valid pipeline the table equals today's `TRANSITIONS`; a test checks that for the default one and a property test checks that no state is entered out of order (develop only after the approval, review only after the tests) for random valid pipelines.
- The table is generated when the job starts and kept in the runner's `Active` record, so the transition check of a running job follows its own pipeline. The check that matters on top of the table is the runner's own step order, and a second property test runs random valid pipelines on a scripted `Steps` and compares the calls with the pipeline.
- A saved pipeline applies to `change` jobs only. The other kinds (`review-branch`, `write-tests`, `document`, `audit-deps`) keep their fixed flows from job-types.

### Where the pipeline is read
- `data/pipelines.json` (`AGENTLIFE_PIPELINES_FILE` overrides it; tests get a scratch file). `PipelineStore` writes like the teams file (temp file + rename, unreadable file moved aside). A project without an entry runs `DEFAULT_PIPELINE`.
- `PipelineService.save` validates against the project's team (400 `invalid_pipeline` with an `issues` entry `steps.<index>` per broken rule). `forJob` validates again when a job starts, because the team may have changed since: a pipeline that no longer holds refuses the job with 409 `pipeline_invalid` and the reason, before anything is recorded. It does not fall back silently to the default pipeline. The same call fills in the member of Research and Second review, so the job keeps them.
- A job keeps its pipeline for its whole life (requirement 2.2). Members are resolved from the team snapshot the job takes at its first step (`TeamService.resolveMember`); a named member who left in between stops the step with a clear message (`memberForStep`) instead of running someone else.
- Routes: `GET /projects/:id/pipeline` (steps, `customised`, and the team members the rules are checked against), `PUT` (body `{ steps }`), `DELETE` (back to the default).

### Optional steps
- Research (`steps/research.ts`): the member runs on the Architect's runtime with its own read-only agent file in a fresh clone of the project. The prompt `prompts/researcher.md` has the untrusted-content rule, the goal and the project memory as fenced data. The notes are cut at 8 000 characters, stored as the artifact `research.md` and handed to the plan step as `ctx.research`; `architect.md` has a `{{research}}` placeholder that holds them fenced (`(none)` without research). The report has a "Research" section in a code block. The step has no `agent.work` card (`research` is not one of the five `StepName`s); its progress lines reach the terminal.
- Second review (`reviewStep` with `ctx.memberId`): the same function and prompt as the review, so the second reviewer never sees the first review and answers independently. Reviews run in the order of the pipeline on every attempt; the job fails if either fails and the Developer's retry gets both sets of notes. Artifacts `second-review-<attempt>.json`; the report has a "Second review" section with its own verdict. Its credits are counted with the review step (same run log key).
- Under `RUNTIME=fake` the fake steps answer research with canned notes and the second review like the review.

### Known limits
- No `agent.work` card for Research, and the second reviewer's card replaces QA's while it works (both sit at QA's seat).
- Firing the reviewer or researcher is not blocked by a pipeline that uses them; the next job is refused with the reason.
- Not run live: the real researcher and second reviewer with `kiro-cli`.

## Decisions made while implementing (task 3)

- Protocol: client `pipeline_state`, `pipeline_save { steps }`, `pipeline_reset`; server `pipeline { state }` (the engine's `PipelineResponse`: steps, `customised`, and the team members the rules check them against); error code `pipeline_error`. The shape of `steps` is checked with `PipelineSchema` when the message is parsed; the fixed rules are checked by the engine. World-server: `PipelineLink` on `EngineLink` (HTTP engine only, like the Library), handlers in the gateway. The gateway sends the pipeline before it opens the board, and answers every save or reset with the new state; a refusal is a `pipeline_error` with the rule text, followed by the pipeline again so the editor shows what is really saved. The lobby has no pipeline (`bad_message`); the scripted engine and the demo say the editor needs the real engine.
- Client: `ui/pipeline-editor.ts` is the first section of the board panel (above the job card, hidden while a document is open in the viewer). Cards show the step, who does it (the themed select of `select.ts`, choices from `memberChoices`) and the model. Reorder: pointer drag on the grip (the nearest card to the pointer is the drop place, `dropIndex`) and the ← → buttons. Add: a button per missing kind; the new step goes after the last step that precedes it in the usual order (`insertIndexFor`), so adding Research or Second review breaks nothing. Live validation uses `validatePipeline` from shared with the members the engine sent.
- The draft lives in the editor's closure, so a job update that re-renders the board keeps it. It is replaced when the engine sends steps that differ from those the draft started from (after a save or a reset). Save is off while a rule is broken or nothing changed; "Discard changes" and "Back to the default" (only when saved) are beside it.
- Tests: pure helpers and the panel with the fake DOM (`pipeline-editor.test.ts`), the panel state, the gateway with a scripted `PipelineLink` (`world-server/test/pipeline.test.ts`), and Playwright (`e2e/pipeline-editor.spec.ts`: real pointer drag, the arrows, the themed menu, and the board with the editor above the job card, with the test playing the server for `pipeline_*`). The scripted engine has no pipeline, so there is no e2e against a real engine here.
- Not looked at in a browser by the user; not run against a real engine and a real job on a customised pipeline.
