# Design notes (multi-runtime)

Built in the Kiro IDE (2026-11-16), not by the conductor: the month's Kiro credits were used up.

## Checked first
Ollama `qwen3.5:4b` and `llama3.1` both answer a `tools` request on `POST /v1/chat/completions` with a `read_file` tool call (about 11 s each). So one runtime that speaks the OpenAI format covers Ollama, LM Studio, Groq, xAI Grok, OpenAI and OpenRouter.

## Pieces
- `shared/src/providers.ts`: `ProviderConfigSchema` (a cloud provider must use https; an `openai-compat` one needs `baseUrl`), `ProvidersFileSchema` (ids unique, `kiro` must be there), `ProviderViewSchema` (what the client sees: no address, no key), `providerModelLabel`.
- `agent-engine/config/providers.json`: kiro, ollama, lmstudio, groq, xai, openai, openrouter. A new compatible API is one entry.
- `providers/registry.ts`: `ProviderRegistry` loads the file, reads keys from the environment by name, builds one `OpenAICompatRuntime` per provider on first use, and answers `views()` (cached 10 s) for `GET /providers` (`providers/routes.ts`). Availability: kiro needs `kiro-cli --version` to work and `KIRO_API_KEY`; a local provider must have a loopback address (`isLoopbackUrl`, as the Ollama intern) and answer `GET /models`, whose model ids become its list; a cloud provider needs its key variable. `runtime(id)` refuses the same cases, so a misconfigured provider never runs.
- `runtimes/openai-compat.ts`: the tool loop. System text = the member's persona, then the fixed `ROLE_INSTRUCTIONS` of the role, then how the tools work. Each round sends the conversation with the tools; tool calls are run by the engine and their results sent back; an answer without tool calls is the step's `output` (reasoning blocks stripped as for the intern). Limits: 40 rounds, the step's timeout (`AbortSignal.any` of the job signal and a timeout), 1.5 M characters of conversation, 100 K characters of answer. 429 and 5xx are retried twice (2 s, 6 s). Errors are `ProviderError` texts without key or address; the provider's own message is cut to 200 characters and token-like strings (and the key itself) are masked, because some APIs quote part of a wrong key. Raw responses go to `<step>.raw.jsonl` like kiro-cli's.
- `runtimes/file-tools.ts`: the sandbox. `list_files`, `read_file` (text only, 2 MB file cap, 60 K characters per answer, line ranges), `search` (case-insensitive, 100 hits, files up to 1 MB), and `write_file` for the Developer only (400 K characters). `resolveInside` accepts relative paths only: no `..`, no drive letter or leading `/`, no Windows-invalid names, and the real path of the file or of its nearest existing parent must be inside the real path of the job folder, so a link cannot lead out. The secret files come from the deny rules of `agents/tiers/read-only.json` (`defaultSecretMatcher`), the same list kiro-cli enforces; walks skip them, links, `node_modules`, `.git` and build folders. A refusal is returned to the model as text ("Refused: ..."), so it can try something else; it is also an activity line.

## Choosing providers (task 2)
- `config/agents.json`: a role is `{ runtime: "kiro-cli" | "fake", model }` as before or `{ provider: "<id>", model }`; without either it is Kiro (`providerOfRole`). `buildRuntimes(config, delay, kiroHome, providers)` gives each role kiro-cli, the fake runtime or the provider's runtime; a provider that cannot work (no key, address not on this computer, unknown id) gets an `UnavailableRuntime` whose every step fails with the reason, so the engine still starts. `usesRealPipeline` is true when any role is not fake; `roleProviders(config)` lists the roles not on Kiro. `GET /config/roles` shows a provider role's id as its runtime.
- Team members: `TeamMember.provider` (absent = Kiro), `HireBody.provider`, `UpdateMemberBody.provider`. `MODEL_ID_RE` now allows `/`, `@` and `+` (OpenRouter paths). Hiring on another provider needs a model (`model_required`); the Kiro model list applies only to Kiro (`checkModel`); an unknown provider is `unknown_provider`; the Night intern cannot get a provider (`provider_fixed`). Moving back to Kiro without a model takes the template's Kiro model. The agent file of a member on another provider names a Kiro model (kept for a switch back, and `kiro-cli agent validate` accepts it). The default team takes the role's provider from the configuration (`defaultProviders`).
- Resolved members always carry `provider` (`kiro` for members on Kiro), so a member on Kiro stays on Kiro when the role's default is another AI; a member on another provider gets its template's persona as `system`.
- `runtimeForStep(deps, role, member)` in `steps/deps.ts`: the member's provider (Kiro → `deps.kiro`), else the role's runtime. A member on a provider that cannot work stops the step with "<name> runs on <label>, which is not available...". Without `deps.providers` (RUNTIME=fake, or an engine built by tests) a member's provider is ignored. `runRole` passes the role's configured model to a provider runtime and labels the step `model (Provider)` (`providerModelLabel`), which the report's run facts and the job card show.
- The pipeline rule for the second review compares `(provider, model)`: the same model name on two providers is two models. `PipelineMember` and `PipelineMemberView` carry the provider.

## HR desk and `pnpm hotel` (task 3)
- `HrState.providers` (the engine's `GET /providers` views) reaches the HR panel through `http-engine.ts`; `hr_do` hire and update carry an optional `provider`. The gateway learns the provider labels (at start and on every HR state) and gives a member on another AI the seat model `model (Label)`, which the team bar and the ghost tooltip already show.
- HR panel (`ui/hr.ts`): `providerChoices` lists the available providers, Kiro first, plus the member's current one marked "(not available)"; with only Kiro listed there is no picker, so a Kiro-only hotel looks as before. `modelsFor` gives the Kiro model list for Kiro and the provider's own list otherwise; changing a member's provider sends the provider's first model. `providerNote` says under the row what the choice means: a cloud AI receives the files the agent reads; a local one keeps everything on the machine; an unavailable one shows the engine's reason. The Night intern has no picker. Hiring on another provider without a model is refused in the panel.
- `pnpm hotel`: reads `GROQ_API_KEY`, `XAI_API_KEY`, `OPENAI_API_KEY` and `OPENROUTER_API_KEY` from the environment or `.env`, gives them to the engine only and masks them in the logs; the world-server and the client get none. `--ai <id>` and `--model <name>` set `AGENTLIFE_PROVIDER` and `AGENTLIFE_MODEL` for the engine, and `loadConfig` (`withProviderOverride`) puts the three roles on that provider for the run (a fake role stays fake; team members keep their own). Without a Kiro key the launcher picks Ollama when it answers, else the first cloud AI whose key is set, so real agents run without Kiro credits. After the engine is up it prints the available and unavailable providers by label from `GET /providers`.

## Live check (2026-11-16)
- DiscordIA, all three roles on Ollama `qwen3.5:4b` (`pnpm hotel --ai ollama --model qwen3.5:4b`): job `task-7e31c4c9` planned, approved, a one-line change, tests in Docker passed, review PASS, report run facts show `qwen3.5:4b (Ollama)` for analyze, develop and review (about 6 minutes in all). The user's working copy stayed on `main`, clean.
- The first two tries failed and changed the loop. The 4B model read the same 10 lines 20 times and then answered with only reasoning (empty `content`); then it answered in prose without the json block, and the step's retry read the project again until the 5-minute timeout. Now: a call repeated with the same arguments is not run again (the model is told so; a `write_file` resets this); 3 rounds before the limit the model is asked for its answer with no tools; an empty answer gets up to 3 more tries without tools; when the task asks for a "fenced block tagged json" and the answer has none, one reminder goes in the same conversation without tools, which is much cheaper than the step's retry.

## Decisions
- **The engine is the sandbox for non-Kiro providers** (D19 in risks-and-decisions.md). kiro-cli enforces the tier from the agent file; for any other provider the model has only the four tools above, run by the engine with the same deny list. Shell and network do not exist for it. The diff validation, Docker tests and plan approval are unchanged and still decide.
- **A cloud provider receives what its agent reads**, as Kiro does today. It is used only when the user set its key, and the HR desk says so when it is chosen (task 3).
- No streaming: one request per round keeps the loop simple and the same for every API.
